| № | Замечание ревьюера | Раздел / ID | Решение | Обоснование |
|---|--------------------|-------------|---------|------------------------------|
| 1 | Порог запуска фоновых задач (cron) для сверки статусов «не чаще 1 раза в 5 минут» нереалистичен. При большом количестве заказов это создаст избыточную нагрузку на API ТК и может привести к его падению. | NFR-P3, LI-2, Раздел 9А | Принято | Изменена логика страховочного опроса: теперь cron-задача опрашивает не все заказы скопом, а только «зависшие» (по которым давно не было webhook). Частота снижена до 1 раза в час (или пачками). Это снижает нагрузку на API. |
| 2 | Нет единого названия для разрабатываемого интеграционного слоя. По тексту приходится писать длинно: «интеграционный слой между ERP и ТК». | Введение, весь документ | Принято | Введен единый термин — **«Сервис логистической интеграции» (СЛИ)**. Заменены все длинные конструкции по тексту для улучшения читаемости документа. |
| 3 | Введение перегружено технической информацией (упоминание PostgreSQL 11, REST-шлюза). Введение должно описывать бизнес-проблему, а не техническую архитектуру. | Раздел 1. Введение | Принято | Технические подробности удалены из введения. Они остались только в разделах «Ограничения» (7.1) и «Нефункциональные требования» (раздел 5). Введение теперь сфокусировано на убытках и проблемах клиентов. |
| 4 | Не учтена передача текстового комментария к заказу (например, «пропуск в коттеджный поселок»). В API ТК нет отдельного поля, это нужно отразить в рисках и совместимости. | NFR-C3 (Совместимость), Раздел 8 (Риски) | Принято | В NFR добавлено требование о передаче комментария в свободном поле API. В Риски добавлен риск RI-14 о том, что если API не поддержит комментарий, информация о пропуске потеряется, и оператор должен продублировать её по телефону ТК. |

| 1 | Необходимо уточнить, что подразумевается под нормализацией адреса. В отличие от телефона, для адреса не определено, какие преобразования выполняются. | EP-2, UC-2 | Принято | Уточнена обработка адреса: в основной поток добавлено разбиение адресной строки на структурированные поля (город, улица, дом, корпус/строение) в соответствии с требованиями API ТК. Также добавлен шаг проверки корректности заполнения полей: наличия обязательных компонентов и отсутствия недопустимых символов. |
| 2 | В альтернативном потоке EP-3 необходимо уточнить обработку ошибки валидации и определить, кого следует уведомлять о проблеме. | EP-3, UC-3, RI-9 | Принято | Скорректирован альтернативный поток обработки ошибки валидации при регистрации отправления. Убрано упоминание кладовщика из процесса обработки ошибки. Вместо этого предусмотрено создание задачи для оператора клиентского сервиса в очереди ошибок согласно RI-9. |
| 3 | Необходимо разделить FE-3 на две самостоятельные функции: регистрацию отправления и просмотр данных зарегистрированного отправления. | Раздел 1, FE-3.1, FE-3.2; раздел 3, EP-3, EP-10; разделы 4–7 | Принято | Исходная FE-3 разделена на FE-3.1 «Регистрация отправления в API ТК» и FE-3.2 «Просмотр данных зарегистрированного отправления в ERP». Для FE-3.1 сохранён EP-3, отвечающий за автоматическую регистрацию отправления и передачу полученных данных в ERP. Для FE-3.2 добавлен новый эпик EP-10 с пользовательской историей и сценарием использования: логист-диспетчер просматривает данные зарегистрированного отправления и трек-номер в ERP. EP-10 связан с бизнес-целями BO-2 и BO-4, ему присвоен приоритет Must have. Обновлены скорректированное дерево функций, таблица соответствия эпиков и функций, анализ сущностей, проверка полноты и атомарности, трассируемость, таблица приоритетов, чек-лист и итоговый перечень эпиков. |

Итоговая версия после ревью: документ пользовательских требований с десятью эпиками (EP-1–EP-10).
